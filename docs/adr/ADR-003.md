# ADR-003 · Capabilities are attributes, interaction is hooks

- **Status:** Accepted (2.0)
- **Context:** 1.x decided what a component could do with `isinstance`
  checks against capability protocols, and interaction entered through one
  untyped `handle(event)` verb. Both were invisible in a signature and hard
  to test in isolation.
- **Decision:** A widget declares `focusable`, `clickable`, `hoverable` and
  `activatable` as class attributes. Input arrives through typed hooks:
  `on_key`, `on_mouse`, `on_paste`, `on_resize`, `on_focus`, `on_click`,
  `on_hover`, `on_drag` and `on_action`.
- **Why:** The router reads flags instead of probing protocols, and a
  behavior can be tested by calling the hook it belongs to. It removes the
  reflection-based "looks interactive" heuristic.
- **Consequences:** Each hook answers `True` only when it consumed the
  input. `on_action` is the one named-action door for keymaps and menus.
  A pure renderer may implement `render` without inheriting the base.
- **Alternatives:** Keep `runtime_checkable` capability protocols; use a
  message bus (rejected: hidden ordering and re-entrancy).
