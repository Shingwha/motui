# ADR-023 · Results are pulled, not pushed

- **Status:** Accepted (2.0)
- **Context:** The demo walks the whole mounted tree every frame to collect
  results. During design we considered adding a per-widget `on_result`
  callback so a widget could push a pick immediately.
- **Decision:** No callback. `Widget.walk()` is public, and a host collects
  with `walk()` plus `take()`. A component that needs to report a result
  leaves it pending on itself.
- **Why:** A push callback re-enters dispatch while an event is being
  routed, which makes ordering and re-entrancy unpredictable. It also
  invites a message bus and a second way to deliver the same fact. A pull
  keeps one door and one order.
- **Consequences:** A host must either walk the tree or keep a reference to
  the controls it cares about. `walk()` is a stable public API. If a real
  need appears later, an App-level single hook or `Modal.on_close` is the
  preferred shape, not per-widget callbacks.
- **Alternatives:** Per-widget `on_result` (rejected: re-entrancy and
  ordering); an App-level result queue (a possible future single hook, but
  not needed in 2.0).
