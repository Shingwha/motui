# ADR-021 · Focus is derived from the tree

- **Status:** Accepted (2.0)
- **Context:** The 1.x focus policy required a host to register targets
  (`set_focus_targets`, `FocusManager.add/remove`) and containers declared
  an owner flag. Mounting a widget did not make it focusable, and the
  registration lists could drift from the rendered tree.
- **Decision:** Focus is derived. A widget joins the ring by setting
  `focusable = True`; the ring is the preorder walk of the mounted trees.
  A `focus_scope` container joins the ring itself and stops the descent.
  `App.focus`, `focus_next` and `focus_previous` are the public entries;
  the manager is internal.
- **Why:** Adding a control to the tree is enough to make it focusable.
  There is no second registration to keep in sync, and focus order is the
  same order a reader walks.
- **Consequences:** Focus order is preorder over pane and dock documents.
  A widget shared in two places appears once. A container that routes its
  own children (`Form`, `Dialog`, `ComboBox`) uses `focus_scope` instead
  of exposing internal targets.
- **Alternatives:** Keep explicit registration (rejected: drift and extra
  API); derive from attribute names (rejected: invisible and fragile).
