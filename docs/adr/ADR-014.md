# ADR-014 · Screen is an ABC

- **Status:** Accepted (2.0)
- **Context:** The 1.x `Screen` was a `runtime_checkable` protocol. Adding
  a method therefore broke every third-party implementation silently at
  runtime, and shared default behavior had to be copied by each host.
- **Decision:** `Screen` is a narrow abstract base class with default
  implementations where a sensible default exists. Hosts subclass it;
  consumers still treat it as a protocol and never use `isinstance`.
  `TerminalScreen` and `HeadlessScreen` are the shipped subclasses.
- **Why:** A host or a test can inherit the common behavior, and a 2.x
  method addition with a default does not break subclasses. Keeping the
  consumer side protocol-shaped avoids a hard coupling to the ABC.
- **Consequences:** Adding an abstract member is a break; adding a
  defaulted member is not. `copy_to_clipboard` already has a declining
  default (`False`) so a custom screen only implements the writes it owns.
- **Alternatives:** Keep a `Protocol` (rejected: no default behavior and
  no safe growth); a concrete base with unimplemented stubs (rejected:
  silent no-op failures).
