# ADR-024 · Pixel is a medium, not kernel core

- **Status:** Accepted (2.1, provisional)
- **Context:** 2.0 shipped `motui.kernel.pixel`, a mutable raster, a palette
  and a quantizer. It is pure and stdlib-only, but only `PixelCanvas` and
  the demo consume it, and it is not part of the shared kernel vocabulary.
- **Decision:** Move the engine to `motui.pixel`, a layer that depends on
  the kernel only. `Raster` owns private slot/heat grids and exposes verbs
  plus `at()`; `PixelCanvas` stays in `widgets` as the adapter. The engine
  is provisional in 2.1 and may change in a minor until it is frozen.
- **Why:** Kernel is a contract, not a folder for pure code. A mutable,
  specialized raster in the kernel enlarges the surface every layer would
  have to care about and makes octant/dither growth a kernel change. A
  medium next to `terminal` keeps the core minimal and the extension point
  explicit. `PixelCanvas` does not belong in the engine: a widget is an
  adapter, not a raster.
- **Consequences:** `import-linter` gets a fifth contract; `api-2.1.txt`
  records the selected engine and adapter methods; the demo no longer
  touches a raster byte array. The cost is one more public package and a
  migration table for the moved names.
- **Alternatives:** Keep a single `kernel/pixel.py` (rejected: mutable
  engine in the core contract); put the engine under `widgets` (rejected:
  it is reusable without a widget); make a generic layer stack now
  (rejected: two named layers are enough until a third consumer exists).
